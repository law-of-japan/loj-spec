# 変更の種類

正本（登録台帳、履歴マニフェスト、版パッケージ、字体注記、再構築報告）への変更の種類と、種類ごとの検査を定める。この検査は、二つの記録版（変更前後の正本のcommit）を比べる変更検査であり、適合レベル（L0〜L4）とは別に報告する。

## CHG-01 変更の種類

| `LoJ-Change`の値 | 意味 | 版パッケージの本文 | Revisionへの影響 |
|---|---|---|---|
| `format` | 書式変更。同じ内容の表現（Markdownの書式・マーカー・ファイル分割）の変更 | 表現だけ変わる。ASTは変わらない | なし |
| `correction` | 記録訂正。LoJの転記・復元の誤りを、原典に照らして直す | 宣言した版のASTが変わる | IDを保つ。記録版の更新 |
| `officialCorrection` | 官報正誤。官報正誤による公布本文の訂正を反映する | 宣言した版のASTが変わる | IDを保つ。記録版の更新 |
| `restoration` | 復元の進展。欠落していた本文を補う | 宣言した版のASTに内容が加わる。本文の状態が変わる | IDを保つ。記録版の更新 |
| `metadata` | 属性・根拠の更新（時点値、出典、確認状態、関係、外部識別子、ラベル、字体注記、再構築報告等）。登録台帳の変更（Recordの登録、仮登録の確定、統合・分割・撤回、番号主張・外部識別子の更新）も含む | 変わらない | IDを保つ |
| `revisionAdd` | 状態の追加。新しい改正による版を加える | 新しい版パッケージが加わる。既存の版は変わらない | 新しいRevision |
| `revisionFix` | 状態の訂正。法令の状態の取り違えの訂正、Revisionの撤回・統合・分割 | 宣言した版が変わる・増える・減る | 撤回・統合・分割の対応を記録する |
| `migration` | 仕様の版の移行。版パッケージを別のschemaVersionへ変換する。新しい版が、旧い版からのASTの対応表を規範として提供する場合に限り使える | ASTの形が変わる | なし |

- 法令の改正に当たるのは`revisionAdd`だけである。官報正誤と記録訂正は法令の改正ではないので、新しいRevisionを作ってはならない（MUST NOT）。
- 官報正誤（公布された本文の訂正）と記録訂正（LoJの記録の誤り）を区別しなければならない（MUST）。官報正誤は、官報正誤を根拠として記録する。
- 種類を一つに決められない変更は、種類ごとに別のcommitに分けなければならない（MUST）。
- 生成器、CIの設定、文書等、正本のデータに触れない変更は、分類の対象外とする。

## CHG-02 種類ごとの検査

ASTは、`schemaVersion`・`law`・`root`への投影を、位置情報を除いて完全一致で比べる。`text`は改行・空白・コードポイント列を含めて比べ、正規化しない。

| 種類 | 変更してよい範囲 | 検査 |
|---|---|---|
| `format` | 版パッケージのファイル（表現） | 変更前後で、すべての版のASTが一致する。履歴マニフェスト・登録台帳は変わらない |
| `correction`／`officialCorrection` | 宣言した版の本文。従属して、その版の字体注記（[GLYPH-04](../../loj-glyphs/v1alpha1/01-glyphs.md)）、その版を指すScopeの`nodes`（[TYPE-08](05-types.md)）、当該Revisionの`text.sources`・`text.glyphCheck`、根拠のSource・Evidence | 宣言していない版のASTが一致する。宣言した版ごとに根拠（原典の箇所、官報正誤）がある |
| `restoration` | 宣言した版の本文と本文の状態。従属して、`correction`と同じファイルと、当該Revisionの`text`の欠落範囲、再構築報告の対応 | 宣言していない版のASTが一致する。本文の状態・欠落範囲の宣言が更新されている |
| `metadata` | 版パッケージ以外のファイル（登録台帳を含む） | すべての版のASTが一致する。登録台帳では、統合・分割・撤回したRecordのIDを再利用していない（[RID-05](../../loj-registry/v1alpha1/02-record-ids.md)） |
| `revisionAdd` | 新しい版パッケージ（本文のない版（`text.status: absent`）では版パッケージを置かない）と、その履歴マニフェストの項目。従属して、新しい版の字体注記、`history.yaml`の新しいRevision・関係（`relations`）・Source、再構築報告の`mappings` | 既存のすべての版のASTが一致する。新しい版が版の順序の要件を満たす |
| `revisionFix` | 宣言した版と、撤回・統合・分割の対応の記録 | 宣言していない版のASTが一致する。撤回・統合・分割した旧IDを再利用していない |
| `migration` | すべての版 | 新しい仕様の版が規範として提供するASTの対応表で変換した旧ASTが、新ASTと一致する |

- 従属するファイルの更新は、宣言した種類の変更に含まれ、別の種類として分けない（[CHG-01](#chg-01-変更の種類)の「種類ごとに別のcommitに分ける」には当たらない）。従属するファイルは、ASTの一致の検査の対象ではない。宣言していない版のASTは、従属するファイルを更新しても、変わってはならない（MUST NOT）。
- 従属して更新できるのは、宣言した版（`revisionAdd`では加えた版）に関する部分に限る。宣言していない版のRevisionの項目、字体注記、再構築報告の対応を変えた場合は、変更検査で不合格とする。
- `loj/v1alpha2`は、`loj/v1alpha1`からのASTの対応表を提供しない。`loj/v1alpha1`から`loj/v1alpha2`への移行は再構築（[REB-01](../../loj-rebuild/v1alpha1/01-rebuild.md)）で行い、`migration`を宣言してはならない（MUST NOT）。

- 誤りが後続の版へ引き継がれている場合、記録訂正は、影響するすべての版を宣言して一度に直してよい（MAY）。
- 異体字・旧字体の新字体への置換、空白や改行の正規化は、ASTが変わるので`format`ではない。原典に照らした`correction`としてだけ行える。
- 変更検査の合格は、変更後の正本がL0〜L4に適合することを意味しない。

## CHG-03 種類の宣言

- 正本の各commitは、変更の種類を、commitメッセージのtrailerで宣言しなければならない（MUST）。

  ```text
  LoJ-Change: correction
  LoJ-Revisions: 98mj5vgx
  ```

- `LoJ-Change`は、一つのcommitに一つだけ置く。値は[CHG-01](#chg-01-変更の種類)の種類とする。
- `LoJ-Revisions`は、対象のrevision_idをカンマと空白（`, `）で区切って並べる。版を対象にしない変更（`format`、登録台帳だけの`metadata`等）では、省略してよい（MAY）。
- commitメッセージとtrailerは、UTF-8で書く。
- 種類の宣言を、ホスティングサービスのラベル等だけに置いてはならない（MUST NOT）。cloneした先でも記録版の履歴として読めるようにするためである。
- 一つのcommitの種類は一つとする。PRを統合するときにcommitをまとめる（squash）場合は、種類が同じcommitに限る。種類の違うcommitを含むPRは、rebaseで統合する。その場合、正本ブランチに並ぶ各commitが、それぞれ単独で変更検査を受ける。
- 正本ブランチへの統合は、正本ブランチの履歴が一本になる方法（squash、rebase）で行う。正本ブランチにmergeのcommit（親が二つ以上のcommit）を置いてはならない（MUST NOT）。種類の宣言を一つのcommitに一つとし、比べる変更前の記録版を親のcommitに一意に定めるためである。
- 法令リポジトリの最初のcommitは、`revisionAdd`とする。変更前の版はないものとみなして検査する（履歴だけで本文のない版を加える場合も同じ）。
- 変更の取り消し（revert）は、前の変更を意味の上で取り消すcommitをいう。`git revert`が生成する差分そのものを指さない。取り消しのcommitは、原則として取り消す変更と同じ種類を宣言し、その種類の検査を受ける。例外は`revisionAdd`の取り消しで、`revisionFix`とする。
  - `revisionAdd`の取り消し: `revisionFix`とし、加えたRevisionを撤回する（`status: retracted`）。Revisionを履歴マニフェストから削除してはならない（MUST NOT。[HIST-10](../../loj-history/v1alpha1/01-history.md)）。版パッケージを削除する差分（`git revert`の差分）は、この要件に反する。
  - `revisionFix`の取り消し（撤回・統合・分割の取り消し）: `revisionFix`とし、Revisionの`status`と`replacedBy`を戻す。Revisionを削除しない。
  - `migration`の取り消し: `migration`とし、旧い版への対応表を規範として提供する版の組に限る。対応表を提供する組がない本版では、`migration`もその取り消しも宣言できない。
  - そのほかの種類の取り消し: 取り消す変更と同じ種類とする（例: `correction`の取り消しは`correction`）。
- mergeのcommit（親が二つ以上）は、比べずに変更検査で不合格とする。
- そのほかの各commitは、その親のcommitと比べて検査する。二つの記録版の間に複数のcommitがある場合は、各commitを順に検査する。宣言のないcommitと、宣言と検査の結果が合わないcommitは、不合格とする。

## CHG-04 ASTを生成できない版

- 一部しか本文がない版や、L1が不合格の版は、ASTを比べられない。このような版を含む変更では、その版についてのAST検査を判定不能と報告し、合格としてはならない（MUST NOT）。
- `format`の自動変換で、ASTを生成できない版のファイルを変更してはならない（MUST NOT）。その版の書式は、ASTを生成できるようになってから変換するか、人のレビューの記録を付けた別のcommitで変換する。後者の場合も、AST検査は判定不能と報告し、レビューの記録で合格に読み替えない。

## CHG-05 適合との関係

- 変更検査は、適合レベルとは別の検査である。L3に含めない。
- 変更検査の結果を、適合レベルの結果として主張してはならない（MUST NOT）。適合の判定は別に報告する。
