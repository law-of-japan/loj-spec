`scripts/verify.py`は、すべての索引・期待結果・正例の入力の形と、要件IDの存在を検査し、v1alpha2の正例のASTを原文と突き合わせる。v1alpha2のL0の正例は、ASTを持たずにL0の`pass`を挙げることと、ManifestがL0の検査を通ることを検査する。期待結果の診断の位置は、`documents`のファイルの中の一つの行（行末の改行を含む）であることだけを検査し（`law.yaml`を指す位置は拒否する。SRC-01はManifestの意味の違反の位置を定めない）、規則が指すべき行かは判定しない。版パッケージのケースを除く負例は、索引の`rejectedBy: schema`の印のとおりに、入力のYAMLがschemaで落ちるか、schemaを通るかを検査する（[CONF-01](../spec/common/v1alpha1/04-conformance.md)）。別の入力の写しに変更を加えて作った入力（索引の`derivedFrom`）は、元に変更を適用し直した結果と一致することを検査する。元の正例だけを直して`author_next_cases.py`を実行し忘れると、ここで失敗する。変更が期待する規則の違反だけを生むかは判定せず、レビューで確かめる。v1alpha2のL1の負例と、L3・L4・登録台帳・再構築報告・変更検査・固定参照のケースの合否は判定しない。検査器で判定する。

### ケースのない要件

次の要件にはケースを作らない（検査の対象外）。

| 要件 | 理由 |
|---|---|
| CORE-01〜05、CHAR-02〜05、VIEW-01〜07 | データの構成・作業・派生処理の制約であり、一つの入力の成否として検査できない。CORE-03（YAML）の違反は各系列の01で、CHAR-01はpkg-106で確かめる |
| CONF-01〜03、VAL-01、VAL-03、VAL-05、VAL-07、VAL-08 | 適合の主張とケースの契約そのもの。資料の監査とレビューで確かめる |
| REB-01〜08 | 再構築の作業の手順。結果は再構築報告（REBR）と履歴マニフェストのケースで確かめる |
| SRCM-01、XREF-04 | 予約の区分 |
| GLYPH-03、GLYPH-07、GLYPH-08 | 本文に置く字の選び方は原典と比べないと判定できない（原典照合） |
| RID-03、REV-02 | リポジトリの名前と可読ラベルは参照の解決に使わない、という制約 |
| TIME-05 | `reason`に書く理由の中身と、確認した範囲（SHOULD）は、レビューで確かめる。`reason`があることはTIME-01の必須のフィールドとして検査する（2026-11-12、[law-of-japan/loj-spec#32](https://github.com/law-of-japan/loj-spec/issues/32)） |
| CHG-05 | 変更検査の結果を適合レベルとして主張しないことは、実装と適合の主張への要求であり、レビューで確かめる（同上） |
| TABLE-02の一部（既存の行の`key`の維持、基礎の版の同じ行が同じ`key`を持つこと） | 行の同一性は法的な判断であり、機械では確かめられない。入力者への要件とする（2026-11-12、[law-of-japan/loj-spec#23](https://github.com/law-of-japan/loj-spec/issues/23)） |

[規範仕様の入口](../spec/README.md#版の状態)の版の状態の定め（要件IDなし）にも、ケースを作らない。仕様の資料そのものの管理の規則であり、法令の入力の成否として検査できないためである。状態の表の形は`scripts/verify.py`が検査する。タグを打つことは、公開の手順（[CONTRIBUTING](../CONTRIBUTING.md)）で確かめる。

機械で検査できるのにケースがない要件は、2026-11-12の時点でない（[law-of-japan/loj-spec#32](https://github.com/law-of-japan/loj-spec/issues/32)の結論（4））。下の段落に、ケースが一部の場合だけにとどまる要件を挙げる。

CHG-04（2026-11-12）は、L1が不合格の版を含む`metadata`の変更を判定不能とする正例（common-025）と、その版のファイルを`format`で変える負例（common-026）がある。一部しか本文がない版、人のレビューの記録を付けた別のcommitでの変換のケースは、まだない。

RID-04・RID-05（2026-11-12）は、統合したRecordを残し、`replacedBy`で登録空間を書いて統合先を指す正例（reg-009）と、大文字を含む登録空間の負例（reg-010）がある。統合・分割・撤回したIDを別のRecordに再利用する負例は、まだない。発行の時の衝突の確認（RID-01）と同じ現象であり、どちらの規則で報告するかが決まっていないためである（[law-of-japan/loj-spec#63](https://github.com/law-of-japan/loj-spec/issues/63)）。

共通の型と時点値（2026-11-12、[law-of-japan/loj-spec#32](https://github.com/law-of-japan/loj-spec/issues/32)）は、履歴マニフェストの中で確かめる。登録空間と版の外部識別子の正例（hist-037）と、リポジトリの所在で指すRecord（TYPE-01、hist-038）、Sourceのidの重複（HIST-02、hist-039）、同じファイルにないSource（TYPE-03、hist-040）、Verificationの未知の状態（TYPE-04、hist-041）、原文のないScope（TYPE-06、hist-042）、精度と書式の不一致（TIME-02、hist-043）、版を対象としない外部識別子（HIST-01・HIST-09、hist-046）の負例がある。確認済みの時点値の根拠（TIME-06）は、hist-013が当たる。登録台帳・再構築報告の中の共通の型の違反のケースは、まだない。

CHG-02・CHG-03（2026-11-12、[law-of-japan/loj-spec#18](https://github.com/law-of-japan/loj-spec/issues/18)）の従属するファイルの更新は、記録訂正で同じ版の`text.sources`を更新する正例（common-024）だけがある。common-024は、宣言した版だけのASTが変わり、従属する更新が宣言した版の`text.sources`に限られ、宣言した版の根拠（`text.sources`の箇所）があるので合格とする。Scopeの`nodes`・字体注記の更新、宣言していない版の従属するファイルを変える負例、登録台帳だけの`metadata`、mergeのcommit、最初のcommit、revertのcommitのケースは、まだない。登録台帳の`git bundle`と、親が二つのcommitを持つ`git bundle`が要るためである。

HIST-12の撤回した関係・内訳の扱い（2026-11-12、[law-of-japan/loj-spec#46](https://github.com/law-of-japan/loj-spec/issues/46)）は、撤回した関係を根拠とする負例（hist-034）、内訳をすべて撤回した関係を根拠とする負例（hist-035）、内訳の一部を撤回した関係を根拠とする正例（hist-036）がある。hist-036は撤回した内訳の`effective`を有効な内訳より前にしているが、期待結果は区分の結果だけで、終了の時点そのものは比べない。撤回した内訳から時点を得る誤りは、hist-036では区別できず、hist-052で区別する（下の段落）。関係を撤回して`termination`の項目を削らない状態はhist-034（L3）で検査する。撤回と削除を同じ変更で行うことを変更の検査で確かめるケースと、撤回の後に`termination`の項目を別の関係に置き換える変更のケースは、まだない。

HIST-12の終了の時点と警告（2026-11-13、[law-of-japan/loj-spec#53](https://github.com/law-of-japan/loj-spec/issues/53)）は、撤回していない内訳を一つに限る規則（HIST-03）の負例（hist-053）と、終了の時点より後に施行される版の警告の正例（hist-052）がある。hist-052は、有効な内訳の時点（1959-04-13）と撤回した内訳の時点（1960-04-01）の間に施行される版を持ち、期待結果にHIST-12の警告を挙げる。CONF-01により、成功するケースに挙げた警告は比べるので、撤回した内訳から時点を得る実装と、最も遅い時点を選ぶ実装は、警告を出さずにこのケースを満たさない。一方、警告を出さないことは比べないので、常に警告を出す実装は区別できない。hist-053の`requirements`のHIST-12は、HIST-03に違反する関係では終了の時点を決めず警告を判定しないことに関わるが、警告を出さないことは比べないので、この点はケースでは検査されない。終了の時点が確定日でない場合の判定不能を数えないことは、条件付きの失効（`pending`）と確定日の版を持つ既存の正例hist-003が当たるので、ケースを加えていない。

HIST-13（2026-11-12、[law-of-japan/loj-spec#23](https://github.com/law-of-japan/loj-spec/issues/23)）は、削った行の`key`を使わずに行を加える正例（hist-031）と、削った`key`を後の版で再使用する負例（hist-032）と、本文が一部しかない版を挟んで飛ばす正例（hist-033）がある。本文のない版・L1が不合格の版を挟む場合、`basedOn`が分岐する場合と、表の番号が変わる場合のケースは、まだない。glyph-004（行の`key`を変えて注記が古くなる）は、字体注記の`node`の解決（GLYPH-04）の負例であり、`key`の維持そのものの検査ではない。

HIST-04・05・08の2026-11-11の追加（[law-of-japan/loj-spec#20](https://github.com/law-of-japan/loj-spec/issues/20)）は、hist-023〜026のほか、`glyphNotes`のパスの不一致（hist-047）、`absent`のRevisionのディレクトリ（hist-048）、同じ関係・同じ施行時点の重複（hist-049）、統合したRevisionを基礎状態とする版（hist-050）、撤回した内訳だけを参照する成立根拠（hist-051）の負例がある（2026-11-12）。分割したRevisionを基礎状態とする版の負例は、統合と同じ規則なので加えていない。

## 要件の名宛人と確かめ方

2026-11-12、[law-of-japan/loj-spec#31](https://github.com/law-of-japan/loj-spec/issues/31)の結論による一覧である。参考であり、要件の本文が正である。要件の本文には区分を書かない（本文と区分が食い違う経路を増やさないため）。一つの要件に性質の違う要求が混ざる場合は、行を分け、「対象」の列に該当する文を示す。
