# DDR-031 旧リポジトリのcommitの上に始めた正本ブランチの変更検査

採用日: 2026-11-24。対象: [CHG-01・CHG-02・CHG-03](../../spec/common/v1alpha1/07-changes.md)、[CORE-01](../../spec/common/v1alpha1/01-overview.md)、[REB-08](../../spec/loj-rebuild/v1alpha1/01-rebuild.md#reb-08-既存の参照の維持と旧形式)。[law-of-japan/loj-spec#163](https://github.com/law-of-japan/loj-spec/issues/163)による。DDR-015（変更の種類と変更検査）とDDR-020（原典からの再構築）を補う。

## 旧履歴の境界

- 問題: 旧リポジトリから移した法令リポジトリのうち、公開済みの祝日法と昭和41年法律第86号の`main`は、旧リポジトリの最初のcommit（宣言を持たない）を親として始まっている。最初のcommitは親のないcommitだけを指していた（[law-of-japan/loj-spec#156](https://github.com/law-of-japan/loj-spec/issues/156)）。そのため、`base`を与えない変更検査（最初のcommitからの検査）では、旧commitが宣言のないcommitとしてCHG-03で不合格になる。最初のLoJのcommitも、親を持つ通常の`revisionAdd`として検査され、`history.yaml`の最上位のフィールドを作ることが範囲の外になってCHG-02で不合格になる。旧commitに宣言を書き足すことも、`main`を作り直すことも、正本ブランチの履歴の書き換え（CORE-01の禁止）になる。
- 選択肢:
  - 旧commitの上に始めることを認める。変更検査が旧履歴の境界（最初のcommitの親）を入力として受け取り、境界とその祖先を検査しない。境界の子を最初のcommitとする（採用）。
  - `main`は親のないcommitから始めなければならないとする。公開済みの二つの`main`が不適合のまま残る。直すには、正本ブランチを作り直す（force push）しかない。
  - 宣言のないcommitが続く先頭の部分を、旧履歴と推定する。宣言のないcommitはCHG-03の違反として報告するものであり、推定に使うと、宣言を書き忘れたcommitが黙って検査の外になる。
  - 再構築報告の`legacy.frozenAt`を境界とする。`frozenAt`は凍結した時点の規定のブランチの先端であり、`main`の親と同じとは限らない。祝日法の`main`は旧`master`の最初のcommitから始まっており、`frozenAt`は`main`の祖先ですらない。`rebuild.yaml`は最初のcommitが作るファイルでもある。
- 判断基準: 公開済みの正本ブランチの履歴を書き換えないこと。宣言のないcommitを黙って検査の外にしないこと。最初のcommitの範囲（`history.yaml`・`rebuild.yaml`の全体を作ること）を、親のないcommitと同じに使えること。リポジトリの別（CHG-03）と同じく、検査の前提をファイルから推定しないこと。
- 採用:
  - 法令リポジトリの正本ブランチは、親のないcommitから始めても、旧リポジトリのcommitの上に始めてもよい（REB-08）。後者の親のcommitを、旧履歴の境界とする。
  - 変更検査は、法令リポジトリの検査で、旧履歴の境界を任意の入力として受け取る。境界と、境界から親を辿って到達できるcommitは旧履歴のcommitであり、正本のcommitではなく、記録版を持たない。宣言のないcommitやmergeのcommitであっても報告しない。
  - 境界を親とするcommitを最初のcommitとし、親のない最初のcommitと同じに検査する（`revisionAdd`の宣言、変更前の記録版がないものとみなすこと、最初のcommitの範囲）。境界のcommitの木にあるファイルは、変更前の記録版のファイルとして比べない。
  - `base`が旧履歴のcommitであれば、最初のcommitから検査する。境界は`head`の祖先（`head`自身を除く）とする。条件に合わない境界を与えた検査は、どのcommitが旧履歴か決められないので、各commitを検査せずに不合格とする。
  - 境界を、ファイル（`legacy.frozenAt`等）やcommitメッセージ（trailerの有無等）から推定してはならない。
  - 登録台帳のリポジトリは旧リポジトリから移さないので、境界を与えない。
  - 適合ケースの索引の変更の入力に、`legacyBoundary`を加える（common-065〜069）。
- 理由:
  - 境界を入力にすれば、旧履歴と正本のcommitの区別が、検査器の推定でなく、移行した人の決めた一つのcommitで定まる。境界より後の宣言のないcommitは、従来どおりCHG-03で報告される。
  - 境界の子を最初のcommitとすれば、law-of-japan/loj-spec#156で定めた最初のcommitの範囲を、そのまま使える。旧履歴の木は旧形式のファイル（READMEや旧`law.yaml`等）を持ち、LoJの記録版ではないので、比べる変更前の記録版はない。
  - 公開済みの`main`を作り直さずに、`base`のない検査を合格にできる。
- 制約:
  - 境界は検査のたびに与える必要がある。共通検証ワークフローや検査器が境界を受け取る方法（呼び出す側の設定、検査器のオプション等）は、本仕様の外で、それぞれのリポジトリで定める。境界を与えずに`base`のない検査をすると、旧commitの上に始めた`main`は不合格になる。
  - 旧履歴のcommitは正本ブランチから到達できるが、記録版を持たない。旧commitを指す固定参照は、そのcommitに当該Revisionがない（`history.yaml`がない）ので解決の誤りとなる（FIXREF-06）。旧commitへのリンクは固定参照ではない（REB-08）。
  - 境界が旧リポジトリのcommitであることは、変更検査では確かめない（旧リポジトリを入力に取らない）。
  - これから移すRecordには、参考の手順（[移行の手順](../migration-from-legacy.md)）で、親のないcommitから`main`を始めることを勧める。追加の入力が要らないためである。始め方を一つに決めることは、運用で扱う。
- 再検討: 境界を正本の中に記録して検査器が読む方法（例: 登録台帳のRecordの属性）が求められたとき。旧リポジトリを入力に取り、境界が旧commitであることを確かめる要求が出たとき。
