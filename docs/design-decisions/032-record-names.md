# DDR-032 登録台帳の名称（法令略称・通称）

採用日: 2026-11-26（草案）。対象: [loj-registry/v1alpha2](../../spec/loj-registry/v1alpha2/01-registry.md)の[REG-06](../../spec/loj-registry/v1alpha2/01-registry.md#reg-06-名称)、[REG-02](../../spec/loj-registry/v1alpha2/01-registry.md#reg-02-recordのファイル)、[RID-03](../../spec/loj-registry/v1alpha2/02-record-ids.md#rid-03-リポジトリの名前と参照の解決)。DDR-018（登録台帳とRecord ID）を補う。

## 名称の置き場所

- 問題: 「祝日法」のような法令略称・通称は、法令に興味を持った一般の人が法令を探すときの入口になる。いまは法令リポジトリのGitHubの説明文（Description）にだけ書いている（リポジトリ管理ガイドライン）。説明文はGitHubの設定であり、正本のデータではない。そのため、検査器で形を確かめられず、出典を書けず、変更の履歴がGitに残らない。閲覧用のサイト等を正本から生成するときにも読めない。
- 選択肢:
  - 登録台帳のRecordに、出典付きの名称の一覧を置く（採用）。
  - 版パッケージ（`law.yaml`）に置く。名称は特定の版の本文ではなく法令そのものを指す名前であり、版ごとに写すことになる。
  - 登録台帳のリポジトリに、仕様の外の表示用のファイルを置く。検査の対象にならず、説明文と同じく出典の形が決まらない。
  - 説明文のままとする。GitHubの仕様に依存し続ける。
- 判断基準: 正本のデータとして検査でき、出典を書けること。題名（版ごとに版パッケージにある。REG-02）と役割が重ならないこと。参照の解決に使われないこと（RID-03）。
- 採用:
  - Recordに`names`（必須、空可）を置く。各項目は`id`、`kind`（`abbreviation`・`commonName`）、`value`、`evidence`（一つ以上）、`verification`を持つ。
  - `evidence`は、確認状態によらず一つ以上とする。番号主張・別名等は未確認なら根拠を空にできる（TYPE-05）が、名称は根拠のない名前を検索の入口に出さないため厳しくした。
  - 名称の訂正と削除はGit履歴で追い、`retracted`の主張を残さない。名称は判断の記録ではなく、表示と検索の値だからである。
  - 題名は`names`に置かない。題名は改正で変わり得るので、版パッケージの`title`を正とする（REG-02）。
  - 同じ`kind`と`value`の組を二つ置かない。`value`は資料の表記のままとし、正規化しない。
  - 名称は参照の解決に使わない（RID-03）。名称の一致から二つのRecordを同一と判断しない。
  - 一覧の順序に意味を持たせない。表示に使う名前の選び方は、表示する実装が決める。
  - どの資料を根拠とするか（評価を含む呼び名を記録するか等）は、運用で定める。
- 理由:
  - 登録台帳は、法令番号（`numbers`）や外部識別子（`externalIds`）のように、版をまたいで法令に付く値を、出典付きで持つ場所である。名称も同じ性質の値である。
  - `evidence`を必須にすれば、名称ごとに根拠の資料と箇所が残る。e-Govの「法令略称」は、公的な資料が示す略称として根拠に使える。
  - 説明文は、登録台帳から生成する表示に変えられる。GitHubに依存するのは表示だけになる。
- 制約:
  - `loj-registry/v1alpha1`は公開した版であり、schemaが閉じているので、`names`を加えられない（CORE-04）。そのため新しい版`loj-registry/v1alpha2`を草案として作った。検査器が対応するまで、実際の登録台帳のRecordはv1alpha1のままとし、名称はまだ記録できない。
  - 名称が使われた期間（題名の改正の前の名前が通称として残る場合等）は、本版では記録しない。必要になったら、期間を持たせるか、版の題名から求めるかを決める。
  - v1alpha2の適合ケースは、名称（REG-06）とその一覧の有無（REG-02）だけを持つ。v1alpha1から変えていない要件のケースは、公開の前に写す（[制限](../limitations.md)）。

## 二つの版を並べて置くこと

- 問題: 公開した版と、その次の版の草案を並べて置くのは初めてである。資料の管理が、次の前提を置いていた。
  - 適合ケースの索引のschema（`common/v1alpha1`）が、`suite`を公開した6つの版の列挙で定めていた。そのため、次の版のケースの索引がschemaに合わない。
  - 一つの系列は一つのディレクトリに属するとしていた（規範仕様の入口の「要件ID」）。`verify.py`は、凍結していない二つの版に同じ要件IDがあると失敗した。
- 採用:
  - 索引の`suite`を、期待結果のschemaの`schemaVersion`と同じパターンにした。法令データの検査の結果は変わらず、変わるのはケースの索引が受け入れられる範囲だけである。公開した版の変更であり、仕様の欠陥の修正として[CHANGELOG](../../CHANGELOG.md)と[制限](../limitations.md)に記録した。
  - 系列は種類に属するとし、同じ種類の版は同じ系列を使うとした。要件IDは版ごとに意味を持つ（規範仕様の入口）ので、意味は変わらない。
  - `verify.py`は、条件の外で禁止するフィールドの表の要件を、schemaの版のディレクトリで引く。同じ種類の別の版の要件は引かない。
  - 両方の版のケースIDは、どちらも`reg-NNN`とする。ケースIDは索引の中で一意である。
