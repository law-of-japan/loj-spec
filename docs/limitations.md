# 制限と検証の境界

## 正式な範囲

- 版パッケージ（`loj/v1alpha2`）のL0・L1: 編〜目、条、項、号、細分1〜10、枝番号、削除条、本則、keyを持つ附則、不透明な附属資料、無番号の項、項・号・細分の本文の中の表、前文と制定文、不透明な目次（[BASIC-03](../spec/v1alpha2/01-overview.md)）。
- L3の履歴構造と根拠、L4の関係の解決・関係の整合・時点の整合（[VAL-05・VAL-06](../spec/common/v1alpha1/03-validation.md)）。
- 登録台帳・再構築報告・変更の種類・固定参照の検査。これらは適合レベルとは別に報告する。

日本法令全体の表現を保証するものではない。

## 未対応・予約

| 対象 | 状態 |
|---|---|
| L2（法令内の参照とファイル間参照） | 予約。合格を宣言できない |
| L3の原典照合（SRCM-01） | 予約。版の本文と原典の一致は、まだ機械で検査しない。旧本文の採用（REB-03）もそれまで行わない |
| L4の条項参照の解決（XREF-04） | 予約 |
| 条を持たない本則、複雑な改正指示、ルビの意味型、図、表のセルの中の項・号・表、入れ子の表 | 版パッケージで未対応。`unsupportedFeatures`に記録し、L1は不合格。その版を持つRecordは、字体注記とScopeの`nodes`を判定できず、L3（根拠）が未完了になる。L3（履歴構造）は影響を受けない（VAL-05、TYPE-07、GLYPH-11）。L1のほかの規則の診断は、参考の集計として報告できるが、適合の主張に使えない（BASIC-03） |
| 別表の内部構造（表の行・セル、見出しの行、結合） | 本版では見送り、次の版（v1alpha3）で扱う（[law-of-japan/loj-spec#27](https://github.com/law-of-japan/loj-spec/issues/27)、DDR-012）。別表は不透明な附属資料として書け、L1は不合格にならない |
| ローマ数字等、DISP-01の表にない細分の表示と、いろは・括弧付きの十進の細分の枝番号 | 未対応（DISP-01）。`unsupportedFeatures`に記録し、L1は不合格 |
| 目次と本文の見出しの一致 | 検査しない（TOC-01）。目次は不透明な本文で、一致は原典照合で確かめる |
| 項の見出し（`（施行期日）`等）、原典で空の表のセル | 書く方法がなく、BASIC-03の未対応の一覧にもない。扱いは未決（[試行の記録](trial-real-laws.md)、[law-of-japan/loj-spec#56](https://github.com/law-of-japan/loj-spec/issues/56)、[law-of-japan/loj-spec#57](https://github.com/law-of-japan/loj-spec/issues/57)） |
| 番号のない第1項で、本文が数字のtokenで始まるもの | 未対応（DISP-01）。`unsupportedFeatures`に記録し、L1は不合格 |
| 明治6年1月1日より前の日付のグレゴリオ暦への換算 | 規則を定めない。`unknown`とし、原表記を記録する（TIME-02） |
| `space.yaml`（登録空間の識別子のファイル）の形 | 定めない（REG-01）。`space`を省略した参照の登録空間は、検査器が入力として受け取る（FIXREF-02） |
| 統合案の§15の論点 | 次期仕様の範囲外。将来の版で扱う |

## 検証の境界

- このリポジトリのCIは、仕様の資料の自己整合の検査である（[CONF-03](../spec/common/v1alpha1/04-conformance.md)）。schema、正例の意味木と位置、L0正例のManifest、L0負例の拒否、負例の診断の位置が行の境界にあること、正例のYAMLのschema、`rejectedBy: schema`の印のある負例がschemaで落ちること（印のない負例はschemaを通ること）を検査する。
- L1負例と、L3・L4・登録台帳・再構築・変更・参照のケースは、形だけを検査する。期待どおりの結果になるかは、検査器（統合案のO-17）ができるまで確かめていない。それまでの確かめ方（別の人による期待結果、検査器からの報告）と、公開の前に検査器で一度実行する手順は、[CONTRIBUTING](../CONTRIBUTING.md#期待結果の確かめ方)にある。schemaで落ちる負例で、schemaの誤りが期待する規則の違反と対応するかは、人が確かめる。変更・参照のケースの`git bundle`の中のYAMLは、印の検査の対象外である。
- 機械で検査できる要件のうち、ケースのないものと理由は[要件との対応表](coverage.md)にある。
- L3の根拠の検査は、出典の記載とその形式を確かめるだけである。出典の内容が判断を裏付けるかは判定しない。L3の合格は、記録の正しさを保証しない。
- 未申告の構造を本文に隠すことを、機械で完全に検出する手段はない。原典照合で確かめる。
- 実際のGitHubの表示、e-Gov XMLとの往復、大規模な性能は検証しない。
- 法令の改正を跨いだ条の同一性は、IDでは保証しない。
- 記録・判断の日時は、commitの日時だけから得る（REG-04、HIST-06）。commitの日時は作者が設定でき、rebaseで変わる。squashで統合すると、ホスティングによっては統合のcommitの日時が統合の時点になり、作業の日時が残らないことがある。本仕様は、ホスティングの統合の記録を根拠にしない。commitの日時を法的な時点には使わない。
- 複数のリポジトリにまたがる変更（改正法の登録、被改正法令の関係と版の追加、改正法の版の追加）は、同時に統合できない。途中の状態は、L4で未取得として現れ、不合格にはならない（VAL-06）。統合の順序と、レビュー中の固定参照を統合の後のcommitに付け替える手順は、運用（リポジトリ管理ガイドライン）で定める（[law-of-japan/loj-spec#33](https://github.com/law-of-japan/loj-spec/issues/33)）。
- 字体注記の`ivd`の必須・禁止と、`sequence`と`recorded`の一致は、schemaでは確かめられず、検査器の責務である。正例・負例はまだない（[要件との対応表](coverage.md)）。
- 正本ブランチのGitのオブジェクト形式は、本版では変えられない（FIXREF-04）。SHA-256への移行の規則は、将来の版で定める。

## 凍結した版（loj/v1alpha1）

`loj/v1alpha1`は凍結した。前文、制定文、表、無番号の項、改正・施行の履歴を扱わない。正式な範囲はL0・L1だけである。内容は変えず、検査器と適合データが対応し続けることも求めない。
