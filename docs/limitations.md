# 制限と検証の境界

## 正式な範囲

- 版パッケージ（`loj/v1alpha2`）のL0・L1: 編〜目、条、項、号、細分1〜10、枝番号、削除条、本則、keyを持つ附則、不透明な附属資料、無番号の項、項・号・細分の本文の中の表、前文と制定文、不透明な目次（[BASIC-03](../spec/v1alpha2/01-overview.md)）。
- L3の履歴構造と根拠、L4の関係の解決・関係の整合・時点の整合（[VAL-05・VAL-06](../spec/common/v1alpha1/03-validation.md)）。
- 登録台帳・再構築報告・変更の種類・固定参照の検査。これらは適合レベルとは別に報告する。

日本法令全体の表現を保証するものではない。

## 未対応・予約

| 対象 | 状態 |
|---|---|
| L2（法令内の参照とファイル間参照） | 予約。合格を宣言できない |
| L3の原典照合（SRCM-01） | 予約。版の本文と原典の一致は、まだ機械で検査しない。旧本文は下書きにだけ使い、原典との照合は人が行って`text.glyphCheck`と再構築報告に記録する（REB-03） |
| L4の条項参照の解決（XREF-04） | 予約 |
| 改正の指示の意味（操作の種類、改正の対象、改正後の本文） | 型付けしない（AMEND-03）。改正の指示は本文として保持し、改正の対象の解決と改正の実行は行わない。被改正法令との関係は、履歴マニフェストの関係（HIST-03）で別に記録する |
| AMEND-03で未対応とした改正規定（改正内容の中の改正規定、二つ以上の群からなる改正内容、改正前後の対照表による改正等）、ルビの意味型、図、表のセルの中の項・号・表、入れ子の表 | 版パッケージで未対応。`unsupportedFeatures`に記録し、L1は不合格。その版を持つRecordは、字体注記とScopeの`nodes`を判定できず、L3（根拠）が未完了になる。L3（履歴構造）は影響を受けない（VAL-05、TYPE-07、GLYPH-11）。L1のほかの規則の診断は、参考の集計として報告できるが、適合の主張に使えない（BASIC-03） |
| 別表の内部構造（表の行・セル、見出しの行、結合） | 本版では見送り、次の版（v1alpha3）で扱う（[law-of-japan/loj-spec#27](https://github.com/law-of-japan/loj-spec/issues/27)、DDR-012）。別表は不透明な附属資料として書け、L1は不合格にならない |
| ローマ数字等、DISP-01の表にない細分の表示と、いろは・括弧付きの十進の細分の枝番号 | 未対応（DISP-01）。`unsupportedFeatures`に記録し、L1は不合格。記録がなければ、DISP-01の違反としてL1は不合格 |
| 号・細分と列記が同じ親に並ぶもの、入れ子の列記、段に分けた列記 | 未対応（LIST-02、[law-of-japan/loj-spec#142](https://github.com/law-of-japan/loj-spec/issues/142)）。`unsupportedFeatures`に記録し、L1は不合格。号・細分と列記の混在は、記録がなければLIST-02の違反としてL1は不合格。入れ子の列記は、記録がなくてもDIR-02の違反になる |
| 目次と本文の見出しの一致 | 検査しない（TOC-01）。目次は不透明な本文で、一致は原典照合で確かめる |
| 矩形でない表 | 未対応（TABLE-04、[law-of-japan/loj-spec#73](https://github.com/law-of-japan/loj-spec/issues/73)）。`unsupportedFeatures`に記録し、L1は不合格。実在の法令に矩形でない表があるかは、網羅的には確かめていない |
| 原典で罫線に囲まれた空の表の欄 | 未対応（TABLE-03、[law-of-japan/loj-spec#57](https://github.com/law-of-japan/loj-spec/issues/57)）。`unsupportedFeatures`に記録し、L1は不合格。上の欄・左の欄が続く箇所は、結合したセルとして書ける |
| 項の見出しがかかる範囲（一つの見出しが続く項にかかる場合） | 記録しない。見出しは最初の項にだけ書く（PARA-02、[law-of-japan/loj-spec#56](https://github.com/law-of-japan/loj-spec/issues/56)）。属性のない第1項と`numbering=implicit`の項では、最初の行に見出しを書いて属性を書き落としても、L1では検出せず、原典照合で確かめる。附則の第1項の`（施行期日）`は最も出やすい形なので、収録の際に注意する |
| 範囲の削除条の中にどの条があったか、結ぶ語の選択 | 記録しない・L1では検査しない（HEAD-04、[law-of-japan/loj-spec#153](https://github.com/law-of-japan/loj-spec/issues/153)）。範囲の削除条は範囲の番号だけを持ち、範囲の中の条（枝番号の条を含む）を列挙しない。結ぶ語を原典どおりに書いたか、条ごとの削除条をまとめて書いていないかは、原典照合で確かめる |
| 改行が引用元の行の区切りか組版か（複数行にわたる引いた字句、二行割りの行の区切り等）、改正の指示の文のない改正規定の範囲 | L1では検査しない（MD-04、AMEND-01、[law-of-japan/loj-spec#143](https://github.com/law-of-japan/loj-spec/issues/143)）。L1は改行を本文として保持すること、`instruction=implicit`の改正規定の形だけを確かめる。改行を書くか、原典に指示の文がないか、どこまでが掲げた規定かは、原典照合で確かめる |
| 番号のない第1項で、本文が数字のtokenで始まるもの | 未対応（DISP-01）。`unsupportedFeatures`に記録し、L1は不合格。記録がなければ、DISP-01（またはPARA-01）の違反としてL1は不合格 |
| 明治6年1月1日より前の日付のグレゴリオ暦への換算 | 規則を定めない。`unknown`とし、原表記を記録する（TIME-02） |
| `space.yaml`（登録空間の識別子のファイル）の形 | 定めない（REG-01）。登録空間の識別子は検査器への入力だけで確定し、`space.yaml`は読まない。入力がなければ、識別子を要する判定は判定不能（VAL-03、[law-of-japan/loj-spec#68](https://github.com/law-of-japan/loj-spec/issues/68)） |
| 時点照会（指定した日・対象・条件に適用されるRevisionを求めること） | 規範にしない（HIST-07、[law-of-japan/loj-spec#69](https://github.com/law-of-japan/loj-spec/issues/69)）。履歴構造の合格は、ある日に適用されるRevisionが一つに決まることを保証しない。照会を提供する実装への禁止は、HIST-07にある |
| 複数の登録空間 | 一度に一つの登録台帳だけを入力とする。他の登録空間のRecordへの参照は未取得になる（VAL-03、XREF-01） |
| 原典資料の実体（画像・PDF等）の識別と保管 | 本版では見送り、次の版で扱う（[law-of-japan/loj-spec#130](https://github.com/law-of-japan/loj-spec/issues/130)）。Sourceは`uri`と`fixed`で所在と固定の手段を書くだけで、実体の内容識別子（ハッシュ）・メディアタイプ・保存先を構造として持たず、同じ実体を複数のRecordで共有する形もない（TYPE-02）。LoJの外の資料の`fixed`は記述の文字列であり、本版には、実体を取得して照合する検査がない。実体を法令リポジトリに置く書き方と、外に置いて`fixed`に固定の手段を書く書き方は、本版のまま使える |
| 官報正誤の前の本文を、正誤の後の本文と並べて参照すること | 定めない。官報正誤は、同じRevisionの記録版を更新し、本文を正誤の後の文言にする（CHG-01の表、GLYPH-07）。正誤の前の本文は、更新の前のcommitを指す固定参照で、当時の記録版として指せる（FIXREF-03）。正誤の前と後の本文を、別のRevisionとして並べて指す手段はない |
| 撤回・統合・分割したRevisionの項目そのものを、別のRevisionの内容に書き換えて旧IDを使うこと | 検出しない。撤回の取り消しと宣言した版の訂正と区別できないので、変更検査の旧IDの再利用の検査の対象にしない（CHG-02、[law-of-japan/loj-spec#189](https://github.com/law-of-japan/loj-spec/issues/189)）。レビューで確かめる |
| 本文のある版を、本文のない版（`text.status: absent`）に改めること | 変更の種類を定めない。`correction`・`officialCorrection`（`text.status`の変更が範囲の外）でも`restoration`（本文を補う変更でない）でも行えない（CHG-02）。記録した本文が誤りで本文を収録しない記録に改める場合の扱いは、次の版で定める |
| 名称（法令略称・通称）が使われた期間、名称の字体 | 記録しない（`loj-registry/v1alpha2`のREG-06。草案）。題名の改正の前の名前が通称として残る場合も、期間を持たない。名称の表記は出典（e-Gov等）の字体のままで、番号主張の`glyphs`に当たる字体注記を持たない |
| 同じ組の法令の間に`amends`と`totallyRevises`を重ねて登録すること、関係から別の関係を導くこと | 規則を定めない。HIST-03は関係ごとのフィールド、置き場所、撤回だけを定め、同じ組の法令の間の関係どうしの規則を持たない。本版の要件は、重ねた登録を禁じも求めもせず、関係の推論の規則も持たない |

公開した版では、この表の対象を扱うことが意味の変更に当たる場合、版番号を上げた新しい版で扱う（CORE-04）。統合案の§15の論点のうち、上の表にないもの（原典の入手経路、仕様の版をまたぐASTの対応表の形式）は、本版のデータの意味に関わらないので、運用か、版を上げるときに決める。

## 検証の境界

- このリポジトリのCIは、仕様の資料の自己整合の検査である（[CONTRIBUTING](../CONTRIBUTING.md#検査)）。schema、正例の意味木と位置、L0正例のManifest、L0負例の拒否、負例の診断の位置が行の境界にあること（規則が指すべき行かは判定せず、別の人による期待結果で確かめる）、正例のYAMLのschema、`rejectedBy: schema`の印のある負例がschemaで落ちること（印のない負例はschemaを通ること）、写しで作った入力（索引の`derivedFrom`）が元に変更を適用し直した結果と一致することを検査する。
- L1負例と、L3・L4・登録台帳・再構築・変更・参照のケースは、形だけを検査する。このリポジトリのCIは、期待どおりの結果になるかを確かめない。組1の6つの版を公開する前に（2026-11-26）、規範のケースをすべて検査器（`loj-validator` `1be397e`）で一度実行し、すべて期待どおりであった。結果は公開のPR（[law-of-japan/loj-spec#193](https://github.com/law-of-japan/loj-spec/pull/193#issuecomment-7184444138)）に添付し、このリポジトリには置かない。その後の確かめ方（別の人による期待結果、検査器からの報告）は、[CONTRIBUTING](../CONTRIBUTING.md#期待結果の確かめ方)にある。schemaで落ちる負例で、schemaの誤りが期待する規則の違反と対応するかは、人が確かめる。変更・参照のケースの`git bundle`の中のYAMLは、印の検査の対象外である。
- 機械で検査できる要件のうち、ケースのないものと理由は[要件との対応表](coverage.md)にある。
- `loj-registry/v1alpha2`（草案）の適合ケースは、名称（REG-06）とその一覧の有無だけを持つ。v1alpha1から変えていない要件（REG-01〜05、RID-01〜05）のケースは、v1alpha1の索引にだけある。公開の前に、v1alpha2の索引へ写す。検査器はまだv1alpha2に対応していない。
- 公開した`common/v1alpha1`の適合ケースの索引のschemaは、2026-11-26まで`suite`を公開した6つの版の列挙で定めており、次の版のケースの索引を受け入れなかった。期待結果のschemaの`schemaVersion`と同じパターンに直した（[DDR-032](design-decisions/032-record-names.md#二つの版を並べて置くこと)）。法令データの検査の結果は変わらない。
- L3の根拠の検査は、出典の記載とその形式を確かめるだけである。出典の内容が判断を裏付けるかは判定しない。L3の合格は、記録の正しさを保証しない。
- 未申告の構造を本文に隠すことを、機械で完全に検出する手段はない。原典照合で確かめる。
- 実際のGitHubの表示、e-Gov XMLとの往復、大規模な性能は検証しない。
- 法令の改正を跨いだ条の同一性は、IDでは保証しない。
- 記録・判断の日時は、commitの日時だけから得る（REG-04、HIST-06）。commitの日時は作者が設定でき、rebaseで変わる。squashで統合すると、ホスティングによっては統合のcommitの日時が統合の時点になり、作業の日時が残らないことがある（統合の操作は、[リポジトリ管理ガイドライン](https://github.com/law-of-japan/loj-repository-management-guideline)で定める）。本仕様は、ホスティングの統合の記録を根拠にしない。commitの日時を法的な時点には使わない。
- 複数のリポジトリにまたがる変更（改正法の登録、被改正法令の関係と版の追加、改正法の版の追加）は、同時に統合できない。途中の状態は、L4で未取得として現れ、不合格にはならない（VAL-06）。統合の順序と、レビュー中の固定参照を統合の後のcommitに付け替える手順は、運用（リポジトリ管理ガイドライン）で定める（[law-of-japan/loj-spec#33](https://github.com/law-of-japan/loj-spec/issues/33)）。
- 字体注記の`ivd`の必須・禁止と、`sequence`と`recorded`の一致は、schemaでは確かめられず、検査器の責務である。正例（glyph-028）と負例（glyph-029〜031）は、このリポジトリでは形だけを検査する（[要件との対応表](coverage.md)）。
- 正本ブランチのGitのオブジェクト形式は、本版では変えられない（FIXREF-04）。SHA-256への移行の規則は、将来の版で定める。

## 凍結した版（loj/v1alpha1）

`loj/v1alpha1`は凍結した。前文、制定文、表、無番号の項、改正・施行の履歴を扱わない。正式な範囲はL0・L1だけである。内容は変えず、検査器と適合データが対応し続けることも求めない。
